# 实施路线与验收标准

本次交付到工程基础和接入决策资料。云方案 A/B/C 仍待用户选择，详见 [方案对比](CLOUD-OPTIONS.md)。下面的步骤是后续计划，不代表相关功能已经完成。

## 0. 工程基础：本次范围

- 统一构建、检查、预览与受控打包入口；移除本机绝对路径依赖。
- 保留组件 ID、版本、原有 UI、正式素材和用户副本。
- 建立统一模型、离线样例、契约测试与 CI。
- 记录云协议证据、可实施方案、宿主能力缺口。

结果以 [验证记录](VERIFICATION.md)为准。CI 配置提交到工程不等于 GitHub 已运行通过。

## 1. 选型验证：先取得真实云数据

用户选定方案后，用一台目标打印机、一个账号区域做受控验证。首版单机，不默认选择设备列表第一台。

- 完成交互认证，包括实际账号需要的验证码/MFA分支；密码、token不进入工程目录。
- 列出绑定设备，由用户选择 ID；保留区域配置。
- 连接云 MQTT或HA状态接口，获得一帧有效遥测。
- 明确记录 token失效时行为，不把无法证实的refresh当作前提。
- 连续观察30分钟，包含空闲、打印中或暂停中的可用状态；不为了测试擅自启动、暂停或改变打印。
- 形成一份脱敏字段清单，标明机型/固件/可用项目，验证缺失项没有被当成0。

成功标准：能持续输出符合[内部契约](../schemas/printer-snapshot.schema.json)的真实快照；它仍不代表屏幕链路已完成。若账号的登录方式不支持，应记录具体阻塞分支，再决定完善认证或换方案。

## 2. 可靠采集器与诊断

按方案选定的依赖和许可证固定版本。实现字段解析、增量合并、AMS ID映射、freshness、重连退避、凭据私有存储和日志脱敏。

需要新增的有意义自动化测试包括：

- 部分消息不清空未更新字段；重连不把旧数值刷新时间。
- 多AMS/槽乱序、空槽、明确删除与缺席的差异。
- 已知机型不支持、真实0、无效负值、缺失和stale的区别。
- 账号/区域/设备切换不串缓存，认证失败停止无效重试。
- 429、服务错误、网络断连、重连后的完整状态恢复。
- 私有响应中的access code/token不进入导出和日志。

成功标准：提供本机可观察输出和明确错误状态；程序可关闭、可重启，无重复后台订阅。若增加HTTP或事件流，先定义并测试真实路由，再补运行手册；当前工程没有这些路由。

## 3. Pet Manager/设备能力验证

这是三个云方案共享的步骤，不能靠更换云SDK绕过。

- 读取目标宿主和固件能力，不凭版本号推测。
- 确认surface变量能否通过通用宿主映射更新；列表rows通道不能直接当作13变量通道。
- 若需要修改Pet Manager/固件，先明确源码位置、范围和验收方式。
- 验证单个真实温度或进度随采集值更新、断连可见，串口访问由宿主统一调度。

成功标准：真实数值与PC快照一致，断连不会继续显示为新鲜。仅保存组件包不算通过。

## 4. 数据状态UI与发布

此时才依据真实数据设计UI调整预览：机型标题、任务状态、unknown/stale/unsupported、AMS选择和多喷嘴选择。用户确认后实施，核对变量配额。

验证13项绑定和三页全部输入；缺失项目明确呈现；检查实机屏幕裁切、中文、字模、颜色和进度条轨道。沿用组件ID，完成正式打包/校验/适用自测后再发布，并由同一组件卡片“保存并同步”。

成功标准分别记录：离线检查、官方解释器、打包、导入、同步、实机运行，不能相互代替。

## 5. 本地MQTT：后续独立提供器

以后新增LAN提供器，复用同一快照、缓存、freshness和显示投影。独立管理IP、SN、Access Code与打印机CA；不将云失效自动改成本地连接，切换由用户明确配置。

验证无云账号时可独立工作；模型输出与云方案保持一致。机型/固件字段兼容仍要单独实测。

## 用户选方案时需要决定的事项

- 是否已有长期运行的Home Assistant；有则C通常成本最低。
- 更重视独立维护边界（A），还是先借助上游机型解析快速获得数据（B）。
- 首个验证账号是中国区还是全球区、使用邮箱还是手机号及是否MFA。这些信息在实施时提供，当前无需提交真实密码或token。
- 第一阶段是否先接受PC快照验证，再推进屏幕传输；这有助于把云协议问题与设备显示问题分开定位。

费用/人日估算、风险和具体建议见 [云端方案](CLOUD-OPTIONS.md)，不在本次自动选定。
