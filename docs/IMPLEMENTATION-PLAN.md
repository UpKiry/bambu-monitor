# 方案 A 实施计划与架构决策

状态：2026-11-18，用户已选择 **A：自研 Bambu Cloud 适配器**。本文是待执行计划，当前没有提供器代码、云登录或设备实时更新。需求与验收分别见 [需求规格](REQUIREMENTS.md)和 [验收矩阵](ACCEPTANCE.md)，新会话从 [交接文档](HANDOFF.md)开始。

## 1. 已确定的决策

| 决策 | 采用方式 | 理由 / 边界 |
|---|---|---|
| 数据源 | Bambu Cloud HTTP＋云 MQTT | 不访问打印机本地 MQTT；本地提供器后续单独实现 |
| 采集实现 | 自研精简 Python 3.11+ 参考采集器 | 便于复用现有 Python 工程和离线测试；不依赖 HA、不封装 pybambu |
| 目标部署 | 首轮开发电脑常驻进程，单账户、显式选定一台打印机 | NAS/容器与跨机服务后续验证，不要求电脑和打印机同一 LAN |
| 数据结构 | 现有内部快照 v1＋PC 内部观测元数据 | 对外 Schema 保持兼容；来源/代次/有效性依据留在 PC，不混入设备协议 |
| 显示职责 | Pet Manager 统一管理传输与实例 | 采集器不直接占用 USB 串口，不把 Python 放入组件包 |
| 宿主实现方式 | M0 后确定原生提供器入口或受控 sidecar/IPC | 自研云端的决策已确定，宿主集成方式仍取决于真实源码和设备能力 |
| 凭据 | 系统密钥库优先；不可用时会话内存 | 首版不默默回退明文文件，不把秘密放 argv、stdout 或配置样例 |
| 只读范围 | 登录、设备发现、遥测订阅和限频初始化请求 | 不提供通用 publish、G-code、加热、暂停/启动、文件或相机能力 |
| 协议维护 | 依据固定参考版本，自行实现必要部分 | 参考事实不等于复制整套内部模型；保留实际复用文件的许可 |

Python 是参考采集器的运行时，不是承诺最终桌面客户端必须附带 Python。若 M0 证明原生 Rust 内置提供器更适合分发，可在保持需求、快照与测试向量一致的前提下记录新的实现决策；不能用换语言重新打开 A/B/C 选型。

## 2. 目标结构与通信边界

```text
本地交互认证 → 私有凭据引用 → HTTP设备发现 → 用户选择设备
                                      ↓
云 MQTT → 原始消息校验 → 按代次缓存/增量合并 → 统一快照
                                               ├→ CLI诊断/离线回放
                                               └→ 宿主适配 → app/snapshot候选路径 → 设备surface
```

所有模块和命令均待实现。建议代码组织如下，M1 可随工程细化调整，当前不要创建不可运行的占位模块：

```text
src/bambu_monitor/
  config.py                 # 非秘密配置与账号区域
  credentials.py            # 密钥库/会话内存，不导出秘密
  cloud/auth.py             # 认证状态机与重新认证
  cloud/api.py              # UID/设备发现，明确超时和错误
  cloud/mqtt.py             # TLS订阅、会话代次与重连
  telemetry/parser.py       # 机型字段→规范化事实
  telemetry/state.py        # 增量/AMS身份/失效规则
  telemetry/snapshot.py     # 内部Schema输出
  projection.py             # 面向显示的有界值与质量，不执行USB
  cli.py                    # 本地交互与诊断入口
```

MQTT 网络线程不执行 USB、阻塞 HTTP 或密钥库交互。它通过有界队列把消息交给状态处理器；状态处理器串行合并并生成不可变快照。退出和账号/设备切换撤销旧 generation，迟到回调被丢弃，最后显式关闭网络客户端和线程。

CLI 诊断优先提供标准输出的单个 JSON 或 NDJSON 快照、标准错误中的脱敏日志；机器输出不混入登录提示。交互认证必须走本地 TTY 或明确的宿主私有表单。暂不预设 HTTP/SSE/WebSocket 路由，只有 M0 明确消费方式后才定义相应 IPC、鉴权和生命周期。

## 3. M0：宿主能力核实是首要关口

### 已取得的证据

以下为本机 PetUI `0.1.232` 的文档和随包 Python 校验器核实结果，不代表目标设备握手或 Rust 生产路径已通过：

| 能力 | 核实结果 | 实施含义 |
|---|---|---|
| 离线组件配额 | 当前声明 p4-quota-v2，13 vars，常规预算16 | 只能说明静态声明可容纳，不证明宿主/线协议也能传16项 |
| composition v1/v2/v3 | 当前校验器runtime vars总数≤8 | 当前13变量不能原样直接接入 |
| service bridge | 标量bindings≤8，精确覆盖vars | 新桥并未自动解决13变量问题；候选能力不能假装普遍可用 |
| PC fetch | 单来源映射≤8；两个来源8＋5的声明校验通过 | 8不是整个PC或硬件绝对上限，须区分单来源与总量 |
| PC fetch网络 | HTTPS公开GET、不能Authorization、本机HTTP拒绝、轮询≥60s | 不能直接替代Bambu认证、MQTT或本机私有服务入口 |
| app/snapshot | 宿主参考记录了变量投影入口 | 需继续核对真实实现、边界、时序和设备接收能力 |
| widget/data | 现有通用路径主要是有界rows列表 | 不能用其成功传列表推断13个surface变量已更新 |

证据来自 PetUI 的 composition/service-bridge/PC-fetch/D-host/配额参考和对应校验器；新会话应以本机实际技能路径重新读取并记录版本，不能把作者电脑绝对路径当作项目依赖。历史协议证据另见 [云协议记录](CLOUD-PROTOCOL.md)。

### M0 工作与产物

1. 核对当前项目与工具版本；读取目标 Pet Manager/固件能力。找不到真实设备时，只完成离线与源码层结论。
2. 找到真实宿主源码入口，追踪实例身份、快照类型/项数/大小、app/snapshot生成与设备接收。安装包中的候选文档不替代生产代码证据。
3. 用**明确标记的合成测试快照**验证一个标量、断连失效和会话切换；它不作为实时数据上屏交付，也不冒充云验证。
4. 验证13项投影加质量状态的预算。v2一般只有16变量，额外状态预算不能忽略；不得默认申请v3或偷偷减少指标。
5. 输出宿主接入决策及影响文件清单，分别标明：仅本仓库、Pet Manager源码、固件、技能/校验器/协商需改哪些部分。

M0 退出条件：接入路径有可复核证据，或者明确记录尚缺的产品源码/设备能力及影响。若需要本仓库之外的产品改动，先向用户展示具体范围；用户未授权前保持只读，不修改安装应用、技能、用户profile或固件。

M0 未完成不阻止 M1–M3 的纯采集器工作。只能承诺 PC 快照，不得承诺完整上屏或未经证实的“无需升级固件”。

## 5. 数据和质量实现决策

沿用 [快照Schema](../schemas/printer-snapshot.schema.json)和 [字段映射](DATA-ADAPTER.md)。PC内部另外维护设备/账号/region/session generation、初始快照完整性、逐字段实际观测时间和可用性依据。不得通过增加快照生成时间延长读数寿命。

增量中的字段未出现时保留其数值和 `updated_at`。但静态/会话属性（例如总层数、AMS信息）不应仅因60秒未变化就判stale；同一有效代次中、已知增量协议下，可持续有效，前提是设备在线/遥测会话具有可靠证据。broker ping和无关info消息不能作设备心跳。重连、换任务和设备离线分别使对应依据失效，直至重新确认。

温度/进度等字段也需结合目标机型上报模式制定策略，不能将“不变”与“没有上报”混为一谈。没有可靠会话存活或初始状态证据时保守标记unknown/stale，并明确诊断原因。`updated_at`始终是字段实际观测时间，即使quality仍valid也不能虚构为现在。

现有配置样例的60秒是待实测的**连接可用性设计阈值**，不是统一逐字段TTL或云推送频率保证。完整规则和测试见需求与验收文档。

## 6. 工程与依赖计划

- 新增采集运行依赖前先确定最小集合：MQTT可评估Paho 2.x、HTTP只选择一种客户端、凭据可评估keyring。当前都未安装为项目运行依赖，不宣称支持到某具体版本。
- 将图像工具与采集器依赖区分，避免在NAS采集部署中无故引入完整桌面图像/HA环境；若调整extras，保持现有check/build入口可用。
- 保留未来LAN提供器接口，实现范围限cloud；不把新source名字当成宿主注册。
- 网络、单调时钟、凭据存储、快照输出可替换，核心缓存与投影不依赖具体GUI或串口。
- 对消息体、队列和日志设置明确上限；HTTP超时和取消、MQTT订阅失败和断线清理必须有测试。
- 同步维护开发/操作文档、错误码、依赖许可和实际能力说明；计划中的CLI/IPC在真正实现前一律标为计划。

## 7. 估算与风险

原方案对提供器4–8人日、宿主2–5人日是选型预算，不是当前完整交付承诺。先用约0.5–1人日完成M0的离线/源码核实，再根据实际缺口细化；缺少源码或硬件时不能给固件改动强行封顶。

主要风险：认证/CSRF变化、token续期不可依赖、机型/固件差异、初始/增量状态歧义、宿主13变量与状态预算、外部源码不可用和实机验收条件不足。对应处理分别是认证状态机、明确重登、固定fixture与兼容报告、观测代次模型、M0预算核查、限定授权范围及分层验收。
